# Introduction

![Status: In Progress](https://img.shields.io/badge/status-In%20Progress-yellow)

**Update 2026-05-09:** Sub-phases 1–6 shipped on branch `feature/agentic-org-phase-1-entity-graph` across commits `3208f2c0..b85de819`. Sub-phase 1 (`EntityGraph` foundation, 13 commits) → sub-phase 2 (`EntityReflector` + projection registry) → sub-phase 3 (12 per-domain projections) → sub-phase 4 (`AppState` wiring) → sub-phase 5 (`/api/entities` read API) → sub-phase 6 (blueprint observatory `/entities` page). Plus sub-phase 7 (executable smoke test as TASK-039 CI proxy + this doc). Test count: 154 baseline → 820+ passing across the entity-graph plane (Python) plus a clean Vite + TypeScript build of the blueprint microsite. Schema rel-direction caveats from sub-phase 3 (the projections' `Money→OWNS→Asset`, `Money→TRANSACTS→Organisation`, `Organisation→TRANSACTS→Organisation`, `Asset→LOCATED_IN→Place` writes that fail at write-time per Kuzu's typed REL TABLE FROM/TO constraints) are exception-isolated by the reflector's outer try/except — entity nodes land cleanly; the impossible rels are silently dropped (audit-logged but workflows do not crash). Phase 2's compose-domain v4 will widen the schema or rewrite the projections to use schema-compatible rel directions.

The control-plane substrate runs **14 registered domains** end-to-end, but they live as disconnected `Workflow.payload` blobs. Hiring writes a Person inside its payload; IT-access reads the same Person out of a fresh payload; Onboarding gives that Person Assets — and none of these workflows know about each other. The blueprint at [`docs/agentic-org-blueprint.md`](../docs/agentic-org-blueprint.md) calls this "a bag of workflows, not an organisation" and lays out a five-plane fix. This plan delivers **Plane 1 — the entity graph** — the persistent, queryable, related layer of the org's nouns (Person, Organisation, Asset, Money, Decision, Place, Period) that every later plane (Function FMs, ambient agents, CEO-FM, cadences) is sand without.

Plane 1 is additive. No orchestrator changes. No payload migration. The reflector subscribes to the existing `EventBus`, reads workflow records from `StateStore.get_workflow(id)`, and projects them into KuzuDB via per-domain projection functions. The graph is the *outside* view; the workflow row is the *inside* view. Per blueprint §10 decision #1 the engine is **KuzuDB** (embedded, MIT, Cypher 9, file-backed at `data/portal/entity_graph.kuzu`) — sqlite is undershooting at the moment the design is locking in 3+ hop traversals. Per blueprint §10 decision #4 `Decision` is a first-class graph node with a **ULID id** persisted; the reflector enforces uniqueness on the natural key `(workflow_id, phase, persona_role)` so re-emits dedupe deterministically without leaking ids downstream.

Per blueprint §9 Phase 1 + §10 decision #8: **POC1 (`expense-claim`) and POC2 (`hiring`) are explicitly excluded** from entity projection. They keep running for the legacy demo. The twelve domains that get projections in this plan are the eleven `fleet-*` synthetic journeys and `creative-campaign`. **Done means: every synthetic-journey workflow, when it completes, has its entities visible in the graph; the blueprint shows the org-graph growing in real time as fleet-\* and creative-campaign workflows run.**

## 1. Requirements & Constraints

- **REQ-001**: A new `EntityGraph` service at `api/server/services/entity_graph.py` wraps an embedded KuzuDB database file at `data/portal/entity_graph.kuzu` (path resolved via the existing `_PORTAL_DATA_DIR` pattern in `api/server/state.py`). Schema matches the blueprint §2 Plane 1 Cypher block verbatim plus the §3 `Workflow → Workflow` self-relation: node tables `Person`, `Organisation`, `Asset`, `Money`, `Decision`, `Place`, `Period`, `Workflow`; rel tables `EMPLOYED_BY`, `MANAGES`, `OWNS`, `TRANSACTS`, `BELONGS_TO`, `LOCATED_IN`, `DECIDED_ON`, `PRECEDENT_OF`, `TOUCHED`, `SUB_WORKFLOW_OF`. Schema is bootstrapped via `CREATE NODE TABLE IF NOT EXISTS` / `CREATE REL TABLE IF NOT EXISTS` on first construction. The `Workflow` node + `SUB_WORKFLOW_OF` rel are *forward-compatible* — declared in this phase so Phase 4's meta-workflow projection (`workflow.sub_spawned` audit subscriber) and `/api/workflows/{id}/tree` endpoint have a place to write to without a P1 schema migration.
- **REQ-002**: `EntityGraph` exposes the v0 contract: `upsert(entity)`, `link(src_id, rel, dst_id, **attrs)`, `get(id)`, `by_type(kind, **filters)`, `linked(id, rel=None)`, `touched_by(workflow_id)`, plus `record_decision(workflow_id, phase, persona_role, verdict, reason, decided_at, source_event, attributes, decided_on=())`. `record_decision` returns the canonical `Decision.id` (ULID) — re-issuing the same `(workflow_id, phase, persona_role)` triple returns the existing id without minting a new one. Additionally exposes three Cypher passthrough helpers consumed by Phase 3's MCP tools and Phase 4's `query_precedents`: `query(cypher: str, params: dict | None = None) -> list[dict]` returning every row; `query_one(cypher, params) -> dict | None` returning the first row or `None`; `find_by_pattern(pattern: str, params: dict | None = None, limit: int = 100) -> list[dict]` wrapping `MATCH … RETURN … LIMIT $limit` if the pattern lacks one.
- **REQ-003**: A new `EntityReflector` service at `api/server/services/entity_reflector.py` subscribes via `EventBus.on_any` at construction. On every `FleetEvent` it (a) resolves the workflow via `StateStore.get_workflow(event.workflow_id)`, (b) looks up the projection function for `workflow.workflow_type` in a `PROJECTIONS` dict, (c) executes it to obtain a list of `EntityWrite | RelWrite | DecisionWrite` ops, (d) flushes them to `EntityGraph`. Unknown `workflow_type` is a silent no-op (entity projection is opt-in per domain).
- **REQ-004**: Per-domain projection functions live one-per-file under `api/server/services/entity_projections/<workflow_type_with_underscores>.py` (filename uses `_` for `-`, e.g. `ap_invoice.py`), each exporting a single `project(workflow: Workflow) -> list[EntityWrite | RelWrite | DecisionWrite]`. The package `__init__.py` builds the `PROJECTIONS: dict[str, Callable]` registry by importing each module and binding `workflow_type → project`. **Twelve modules** ship in this plan: `ap_invoice`, `contract_renewal`, `contract_review`, `creative_campaign`, `employee_onboarding`, `it_access_request`, `perf_review`, `privacy_dpia`, `purchase_order`, `travel_preapproval`, `treasury_fx`, `vendor_kyc`.
- **REQ-005**: A one-shot bootstrap runs at `AppState.__init__` immediately after `EntityGraph` is constructed and before `EntityReflector` is started. It reads `data/synthetic/employees.json` into `Person` nodes, `api/server/fixtures/vendors.json` into `Organisation(kind="vendor")` nodes, `api/server/fixtures/agencies.json` into `Organisation(kind="agency")` nodes. Each bootstrapped entity is written with `source_workflows=["bootstrap"]` so reflector-driven updates can append the real workflow id later without overwriting provenance.
- **REQ-006**: A new read-only HTTP surface at `api/server/routes/entities.py` exposes exactly five endpoints, mirroring `api/server/routes/workflows.py`'s shape (FastAPI `APIRouter(prefix="/api/entities")`, `model_dump(by_alias=True)` camelCase responses): `GET /api/entities` with `?kind=<str>&limit=<int>`, `GET /api/entities/{id}`, `GET /api/entities/{id}/linked` with `?rel=<str>`, `GET /api/entities/touched-by/{wf_id}`, `GET /api/entities/_stats` (returns counts by kind, top-10 hot entities by `len(source_workflows)`, recent links).
- **REQ-007**: The blueprint observatory microsite (`web/blueprint/src/`) gains an `Entities` view addressable via `?view=entities` (pattern lifted from the existing `ConstellationPage` switch in `web/blueprint/src/App.tsx`). The page consumes `/api/entities/_stats` and `/api/entities?kind=...` and renders kind counts, recent-links pulse, and a kind-filterable list of nodes. It is the most honest live demo of "this is a substrate, not a bag of demos."
- **REQ-008**: Smoke-test acceptance — running `./scripts/profile-autonomous.sh` for ≥5 minutes produces (a) `Person`, `Organisation`, and at least one of `Asset` / `Money` / `Decision` nodes in the graph file, (b) at least one `Decision` node per HITL-bearing synthetic-journey domain that completed, (c) `/api/entities/_stats` reports a non-zero count for every node table that has at least one synthetic-journey domain projecting into it, (d) the blueprint `?view=entities` page renders the live counts.
- **REQ-009**: Per blueprint §3 unified-data-model the workflow row is the inside view and the entity graph is the outside view — both must coexist without rewriting either. The reflector therefore never mutates `Workflow` records and never writes through `StateStore`; its only writes go to `EntityGraph`, the `EventBus` (as `entity.*` / `decision.*` events), and the `AuditLogger`.
- **REQ-010**: Projection functions are pure — same workflow record in, same list of writes out — so they can be unit-tested without a live KuzuDB instance. Each projection module's test constructs a `Workflow` directly from a fixture record, calls `project(workflow)`, and asserts on the returned ops list. The graph is only stood up in the reflector + read-API tests.
- **SEC-001**: Every entity write is published to the `EventBus` as a non-waking event: `entity.upserted` (carries `entity_id`, `kind`, `workflow_id`, `source_event`) and `entity.linked` (carries `src_id`, `rel`, `dst_id`, `workflow_id`, `source_event`). Both events are appended to the `AuditLogger` chain via `app_state.audit.log("entity.upserted", {...})` / `app_state.audit.log("entity.linked", {...})` so the same hash-chain that protects workflow events covers entity reflections.
- **SEC-002**: Every Decision node write also emits `decision.recorded` carrying the minted `decision_id` (ULID), `workflow_id`, `phase`, `persona_role`, `verdict`, `reason`, `decided_at`, and `source_event`. The reflector calls `app_state.audit.log("decision.recorded", {...})`. Re-emits (the dedupe path in `record_decision`) emit a `decision.deduped` audit entry with the existing ULID — silent overwrites are forbidden.
- **SEC-003**: All three new event types (`entity.upserted`, `entity.linked`, `decision.recorded`, `decision.deduped`) are added to the `FleetEventType` documentation literal in `api/shared/events.py` for searchability, but **not** added to `WAKE_TYPES` — entity reflections are not signal that should wake the FM.
- **SEC-004**: The reflector and bootstrap respect the governance kill switch. Both code paths run under actor `reflector.entity_reflector` / `reflector.entity_bootstrap` so an operator can quiesce entity writes with `kill --actor=reflector.* --tool=*` (the wildcard reach pattern documented in `api/server/services/governance/kernel.py`'s kill-switch lookup at L342-353). The reflector calls `app_state.governance.evaluate(actor="reflector.entity_reflector", tool="entity.write", ...)` before each flush; a deny short-circuits the flush and emits `entity.write.killed`.
- **CON-001**: POC1 (`expense-claim`) and POC2 (`hiring`) produce **no entities**. There is no `expense_claim.py` and no `hiring.py` projection module. Per blueprint §10 decision #8 they continue running for the legacy demo; the reflector silently no-ops when their `workflow_type` arrives.
- **CON-002**: No payload migration of any existing domain. The reflector reads `workflow.payload`, `workflow.metadata`, `workflow.claim`, `workflow.invoice` exactly as they exist today (`api/shared/types.py` `Workflow` model). Projection functions are read-only over the workflow record.
- **CON-003**: KuzuDB is added via the Python wheel `kuzu` (MIT, ~30MB). No external server, no docker dependency, no schema migration tool. Embedded only.
- **CON-004**: No tenancy. Per blueprint §10 decision #3 the design is one-repo-per-customer; `entity_graph.kuzu` is a single file per fork. The path is parameterised via `_PORTAL_DATA_DIR` only because that is the existing portal-artefact convention, not because we expect to multiplex.
- **CON-005**: No new external dependency beyond `kuzu`. ULID minting uses the existing stdlib (`time_ns()` + `secrets.token_bytes(10)` Crockford-encoded — implemented inline in the new `_ulid()` helper in `entity_graph.py`, ≤25 lines, no third-party `python-ulid` package).
- **CON-006**: No changes to any orchestrator file in `api/functions/workflows/`. No changes to `StateStore`, `EventBus`, `AuditLogger`, `GovernanceKernel` public APIs. Wire-up is additive in `api/server/state.py` only.
- **GUD-001**: Single source of truth for projections is `api/server/services/entity_projections/<workflow_type>.py`. There is exactly one `project()` function per file. Hand-written this round; per blueprint §9 Phase 2 `compose-domain` v4 will auto-generate them going forward.
- **GUD-002**: The reflector reads the full workflow record via `StateStore.get_workflow(id)` rather than re-parsing event payloads. This guarantees the projection sees the latest committed state and lets a single `workflow.completed` event drive a complete projection rather than a series of partial ones.
- **GUD-003**: Idempotency is **last-write-wins for entities** (re-running the same projection over the same workflow re-upserts identical attributes; `source_workflows` is appended deduplicated) and **natural-key dedupe for Decisions** (`record_decision` checks `(workflow_id, phase, persona_role)` first, returns the existing ULID on hit).
- **GUD-004**: All entity ids are namespaced by kind: `PERSON-EMP-0042`, `ORG-vendor-acme`, `ASSET-laptop-MAC-92x`, `MONEY-INV-2026-00001`, `DECISION-<ULID>`. Existing fixture ids (e.g. `EMP-0042`) keep their core; the kind prefix is added by the projection helper so cross-kind id collisions are impossible.
- **PAT-001**: ULID minting + Decision dedupe pattern — inside `EntityGraph.record_decision`, in one Kuzu transaction: (1) `MATCH (d:Decision {workflow_id: $w, phase: $p, persona_role: $r}) RETURN d.id LIMIT 1`; (2) if hit, return existing id; (3) else mint `_ulid()` and `CREATE (d:Decision {...})`. Lock per-`(workflow_id, phase)` to make the check-then-mint sequence safe under the reflector's single-threaded bus dispatch — the bus is currently in-process synchronous, but the lock is cheap insurance for future async dispatch.
- **PAT-002**: Projection function signature is uniform across all 12 domains: `def project(workflow: Workflow) -> list[EntityWrite | RelWrite | DecisionWrite]`. `EntityWrite`, `RelWrite`, `DecisionWrite` are tiny `@dataclass(frozen=True)` records defined in `api/server/services/entity_projections/__init__.py`. The reflector iterates the returned list and dispatches each op to the matching `EntityGraph` method. No projection function ever touches `EntityGraph` directly — they are pure functions of the workflow.
- **PAT-003**: Bootstrap pattern — `EntityGraph.bootstrap_from_fixtures(employees_path, vendors_path, agencies_path)` is a one-shot method called by `AppState.__init__` immediately after the graph is constructed. It writes every fixture record with `source_workflows=["bootstrap"]` and emits a single `entity.bootstrap.completed` audit entry summarising counts. Idempotent: re-running on an existing graph file re-upserts (last-write-wins) without duplicating relationships.
- **PAT-004**: Source-workflows append-dedup pattern — every `EntityGraph.upsert(entity)` reads the current `source_workflows` list off the existing node (if any), unions it with `entity.source_workflows`, and writes back the deduped list. This is what lets `bootstrap` populate `["bootstrap"]` and a later workflow projection extend it to `["bootstrap", "VKY-0042"]` without ever overwriting either side.
- **PAT-005**: Projection-function naming — each module's exported function is named `project` (not `project_<domain>`). The dispatch table keys on `WORKFLOW_TYPE`, not on function name, so a grep for `def project(workflow:` returns exactly twelve hits at the end of Phase 3 — a structural invariant that makes audit + future codegen trivial.
- **PAT-006**: Decision `decided_on` semantics — every `DecisionWrite` carries a tuple of entity ids the decision is *about* (the vendor in a KYC sign-off, the person + asset in an access grant, etc.). `record_decision` writes one `DECIDED_ON` rel per id. This is the substrate Phase 4 precedent queries will traverse to surface "this persona's prior decisions on this vendor."
