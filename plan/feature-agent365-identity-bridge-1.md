# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

[feature-agent-governance-toolkit-1.md](feature-agent-governance-toolkit-1.md) landed AGT as the substrate's runtime governance core: every MCP tool call routed through `GovernanceKernel.evaluate_tool_call`, every machine agent declared in [api/shared/agents.py](../api/shared/agents.py) with an Ed25519 keypair persisted under `azurite-data/agt-keys/`, every action ledger entry JWS-signed and hash-chained, every authority resolution evaluated in-process, every workflow's audit blob `agt verify`-able end-to-end. That gave us the deterministic policy core and the cryptographic spine.

What it did not give us is **tenant identity**. Each agent's `did:mesh:<id>` is a self-issued mesh artefact — useful for cryptographic chaining and inter-agent trust but unknown to Microsoft Entra, invisible in the org chart, unable to receive a Teams @mention, unable to send an email from its own mailbox, unable to participate in Conditional Access policies, unable to consume governed Microsoft 365 MCP servers (Mail, Calendar, SharePoint, Teams) under admin control. Agents today live in a parallel identity universe to humans.

Microsoft [Agent 365](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/agent-365-sdk) (GA at Ignite 2025) is the tenant-grade identity, observability, notifications, and tooling layer purpose-built for that gap. Each agent gets an **Agent Blueprint** (Entra app registration), an **Agent Instance** (service principal), and an optional **Agent User** (`agent@tenant.onmicrosoft.com`, full M365 member with mailbox, OneDrive, Teams presence, and `idtyp=user` tokens). Agent 365 ships a Python SDK (`microsoft-agents-a365-*` packages) covering identity, OAuth flows (agent-identity and OBO), MCP tooling for governed M365 servers, OpenTelemetry observability, and notifications across Teams/Outlook/Word.

This plan **bridges the two**, deliberately treating them as orthogonal layers — AGT remains the **policy + cryptographic audit core**, Agent 365 becomes the **tenant identity + presence + transport layer for in-tenant resources**. The integration surface is narrow by construction: one new field group on `AgentRegistryEntry`, one new `Agent365Provisioner` constructed at boot, one extension to the existing two MCP chokepoints (`call_mcp` and `@traced_tool`) that routes a known subset of tool ids through the Agent 365 tooling SDK with the agent's Entra token instead of a raw `httpx.post`. Every kernel decision still happens first; every JWS signature still uses the same Ed25519 mesh key; every audit-chain entry is still verifiable by `agt verify`. The Entra layer adds capabilities; it never relaxes existing guarantees.

The plan is shipped as **future expansion** — engagement-POC scope, not the Zava demo path. CON-000 of the AGT plan applies: the demo build keeps `azurite-data/agt-keys/` and stays AGT-only. This plan turns on at engagement kickoff when a real Entra tenant is available; it must be re-runnable from scratch against any tenant without code changes.

The end-state surface is:

- Every `AgentRegistryEntry` carries `did: str` (existing, derived from `agent_id`), `entra_agent_id: str | None`, `entra_user_upn: str | None`, `entra_blueprint_id: str | None`, `tenant_id: str | None`. All four Entra fields default `None` so the Zava demo path keeps working unchanged.
- Boot acquires (or refreshes) an Entra token per provisioned agent via `microsoft-agents-a365-runtime` using `DefaultAzureCredential` — same auth pattern as [api/server/services/audit_logger.py](../api/server/services/audit_logger.py).
- A new `tools.yaml` field `transport: "mesh" | "agent365"` decides per-tool which transport the chokepoint uses. Default is `mesh` (current behaviour, raw `httpx.post` to mock or live MCP). M365 MCP tools (Mail, Calendar, SharePoint, Teams) get `transport: agent365` and route through `microsoft-agents-a365-tooling-extensions-agentframework` with the agent's Entra token. Kernel decision still happens before either transport.
- Notifications gain a third path: `agent365.send_teams_mention(...)` for in-tenant comms (replaces `graph.send_mail` to a shared inbox for SSC-reviewer escalations). Existing ACS path stays for external-only.
- AGT trust score becomes a **Conditional Access signal**. A score-drop callback in the `RewardEngine` writes the new score to a custom Entra security attribute on the agent's service principal; a published Conditional Access policy (`block-agents-below-300`) blocks token issuance for agents in the `at-risk` group. Score recovery rejoins them. So "rogue agent" containment fires across both planes simultaneously; the Entra credential cannot be used to bypass the mesh kill-switch.
- A new `GET /api/governance/agents/{agent_id}/identity` endpoint returns both facets — `{did, entra_agent_id, entra_user_upn, trust_score, tier, conditional_access_state}` — for the operator UI.
- A new `make agt365-provision` target idempotently provisions all `AgentRegistryEntry` rows with `entra_blueprint_id` set against the current tenant, and a `make agt365-verify` target asserts every provisioned agent's mesh DID and Entra ID resolve to the same human sponsor and same `allowed_tools`.

Each phase ships independently green. Phase 2 introduces the `Agent365Provisioner` against the Microsoft Graph dev-tenant in **dry-run mode** (logs what it *would* provision; never calls Graph) so the existing 128/128 governance test suite keeps passing without an Entra tenant. Phase 5 flips dry-run off behind `AGENT365_PROVISION=1`. Phase 7 is the Conditional Access wiring — the bit a CISO will actually want to inspect. Every phase preserves the Zava demo profile (`AGENT365_PROVISION=0`, default).

## 1. Requirements & Constraints

- **REQ-001**: `AgentRegistryEntry` in [api/shared/agents.py](../api/shared/agents.py) MUST gain four optional fields: `entra_agent_id: str | None`, `entra_user_upn: str | None`, `entra_blueprint_id: str | None`, `tenant_id: str | None`. All four default `None`. Every existing test site that constructs `AgentRegistryEntry` MUST pass without modification — back-compat is non-negotiable.
- **REQ-002**: A new `data/policies/tools.yaml` field `transport: Literal["mesh", "agent365"]` (default `"mesh"`) MUST be added to every entry. `"agent365"` tools route through `microsoft-agents-a365-tooling-extensions-agentframework`; `"mesh"` tools keep the existing `httpx.post` path. The kernel decision in [api/functions/graphs/_common.py](../api/functions/graphs/_common.py) `call_mcp` and [api/server/mcp_tools/_otel.py](../api/server/mcp_tools/_otel.py) `@traced_tool` MUST happen before transport selection. No third chokepoint may exist.
- **REQ-003**: A new `Agent365Provisioner` class (constructed once at boot in [api/server/services/governance/boot.py](../api/server/services/governance/boot.py) alongside the kernel) MUST own all Microsoft Graph calls for Entra Agent Blueprint / Instance / User CRUD. The provisioner is the *only* import site for `microsoft.agents.a365.*` packages across the codebase, mirroring CON-002 of [feature-agent-governance-toolkit-1.md](feature-agent-governance-toolkit-1.md).
- **REQ-004**: Boot MUST run the provisioner in **dry-run mode** by default (`AGENT365_PROVISION=0`). Dry-run logs intent to stdout (`agent365: would create blueprint=<name> for did=<did>`) and writes nothing to Graph. `AGENT365_PROVISION=1` flips it to live mode; the ENV gate is the only switch.
- **REQ-005**: When `AGENT365_PROVISION=1`, boot MUST be **idempotent**. Re-running against an existing tenant detects existing blueprints by `displayName == agt-<agent_id>` and reuses them; never duplicates. A `--force-reprovision` Make target exists for clean-slate testing but is operator-gated.
- **REQ-006**: For every agent that requires M365 resource access (declared by a new boolean field `requires_m365_user: bool = False` on `AgentRegistryEntry`), the provisioner MUST create an Agent User child of the Agent Instance with UPN format `agt-<agent_id>@<tenant-domain>`. Per [Agent 365 docs](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity), the link is immutable — a deleted instance cascades to delete the user. The license assignment step is operator-gated (assigning Microsoft 365 E5 / Teams Enterprise has cost implications) and emits a `LicenseRequired` event the operator UI surfaces.
- **REQ-007**: A new HTTP endpoint `GET /api/governance/agents/{agent_id}/identity` MUST return `{agent_id, did, entra_agent_id, entra_user_upn, tenant_id, trust_score, tier, conditional_access_state, license_assignments, last_provisioned_at}`. The endpoint reads from the in-memory provisioner cache (no Graph round-trip per request). Operator-authenticated, same pattern as `/api/governance/kill`.
- **REQ-008**: The chokepoint extension MUST add OTel attributes `apex.agent.entra_id`, `apex.agent.tenant_id`, `apex.tool.transport` to every span when transport is `"agent365"`. Existing `apex.agent.label` and `apex.agent.did` attributes are preserved. The OTel SDK switch from our hand-rolled decorator to `microsoft-agents-a365-observability-extensions-agent-framework` is **out of scope for this plan** (separate plan if pursued); we keep the existing decorator and add the attributes inside it.
- **REQ-009**: A new `RewardEngine.on_score_change(callback)` registration MUST be wired by `init_governance()` to push score updates into Entra. The callback writes the score to the agent service principal's `customSecurityAttributes.agt.trustScore` field (Microsoft Graph PATCH). Below `TRUST_REVOCATION_THRESHOLD` (300, from `agentmesh.constants`) the callback ALSO adds the principal to the `agt-at-risk` Entra group; above 500 (`TRUST_WARNING_THRESHOLD`) it removes it. A pre-published Conditional Access policy `agt-block-at-risk` blocks token issuance to that group.
- **REQ-010**: A new HTTP endpoint `POST /api/governance/agents/{agent_id}/revoke {ttl_seconds, reason}` MUST trigger BOTH the existing AGT kill-switch (per `/api/governance/kill`) AND an Entra service principal `accountEnabled=false` PATCH for the duration. After TTL, both are reversed automatically by a background task. Operator-authenticated.
- **REQ-011**: A new `tests/api/server/services/governance/test_agent365_provisioner.py` MUST cover dry-run mode comprehensively (no live tenant required). Live-mode tests are skipped unless `AGENT365_LIVE_TENANT_ID` is set; the CI nightly build sets this against the engagement-POC dev tenant only.
- **REQ-012**: The autonomous demo loop, the `make up` boot path, and the canonical 128/128 test suite from [feature-agent-governance-toolkit-1.md](feature-agent-governance-toolkit-1.md) MUST remain green after every phase with `AGENT365_PROVISION=0` (the default).
- **SEC-001**: Entra OAuth tokens MUST NEVER be logged, included in audit blobs, or returned over any HTTP endpoint. The provisioner cache stores tokens in-memory only; tokens expire and refresh per `microsoft-agents-a365-runtime` defaults.
- **SEC-002**: The `Agent365Provisioner` MUST fail closed. Failure to acquire a token at boot when `AGENT365_PROVISION=1` is a fatal startup error, never a silent fallback to mesh-only. Failure to PATCH a trust-score attribute is logged but does not crash the kernel — the mesh-side revocation already fired and is sufficient.
- **SEC-003**: Entra app registrations created by this plan MUST follow the principle of least privilege. The Agent Blueprint requests only the Microsoft Graph scopes that map to tools the agent's `allowed_tools` actually contains. The provisioner asserts this mapping at construction; missing scopes are a fail-closed startup error.
- **SEC-004**: Custom security attributes (`agt.trustScore`, `agt.tier`) MUST be defined in a single attribute set `agt-governance` published once via Make target `make agt365-bootstrap-tenant`. The set definition is committed under `data/governance/entra/attribute-set.json` and is itself operator-managed (Entra IT admin runs `make agt365-bootstrap-tenant` once per tenant).
- **SEC-005**: No org-specific identifiers, agency names, or proprietary process language in any new file. Reviewer must `grep -riE 'wpp|vml|ogilvy|wunderman|groupm|hogarth|kantar' api/server/services/governance/ data/governance/entra/` and find zero hits. Mirrors SEC-005 of [feature-agent-governance-toolkit-1.md](feature-agent-governance-toolkit-1.md).
- **SEC-006**: The Conditional Access policy text committed under `data/governance/entra/conditional-access-policy.json` MUST be reviewed by the engagement security lead before a `make agt365-publish-ca-policy` ever runs against a real tenant. The Make target prints the policy and requires explicit `--i-have-reviewed-the-policy` flag.
- **CON-000**: **Zava demo profile is unaffected.** Default ENV is `AGENT365_PROVISION=0`; default `transport` on every existing tool is `"mesh"`. The demo path is the AGT-only path. This plan exists to be turned on after engagement kickoff.
- **CON-001**: Microsoft Agent 365 SDK packages are GA but young (released Ignite 2025). We hard-depend on the documented Python packages (`microsoft-agents-a365-runtime`, `microsoft-agents-a365-tooling`, `microsoft-agents-a365-tooling-extensions-agentframework`, `microsoft-agents-a365-notifications`, `microsoft-agents-a365-identity` if released). API churn is possible; the `Agent365Provisioner` is the only import site, so upgrades are a single-file diff.
- **CON-002**: Entra Agent Blueprint creation requires Global Admin or Privileged Role Admin. The provisioner refuses to run live-mode without a token whose `roles` claim includes one of these. In dev tenants only the engagement security lead has these roles.
- **CON-003**: Agent User creation incurs M365 license cost (E5 + Teams Enterprise + Copilot for full presence). Phase 5 emits LicenseRequired events; license assignment is a separate operator-gated Make target (`make agt365-assign-licenses`) NEVER auto-run by boot.
- **CON-004**: This plan does NOT migrate the existing audit-blob storage to Entra-managed identity. Storage authentication continues to use `DefaultAzureCredential` as today. A future plan may swap if Entra Agent IDs become valid blob auth principals.
- **CON-005**: This plan does NOT replace the existing OTel decorator with `microsoft-agents-a365-observability-extensions-agent-framework`. That swap is a separate plan with its own back-compat surface; here we only add Entra-specific span attributes.
- **CON-006**: This plan does NOT touch POC3. The integration is generic (operates on `AgentRegistryEntry`); when POC3 adopts the AGT governance core per [docs/governance-poc3-adoption-guide.md](../docs/governance-poc3-adoption-guide.md), it inherits Agent 365 bridge support automatically by adopting this plan.
- **CON-007**: The Conditional Access integration (Phase 7) requires a customer Entra tenant with custom security attributes feature enabled (P1 license minimum). Phase 7 is the only phase with this hard dependency; Phases 1–6 work on a dev tenant without it.
- **GUD-001**: `Agent365Provisioner` is a frozen-dataclass-style singleton constructed at app startup, mirroring `GovernanceKernel`. One module-level instance via `governance.agent365_provisioner()` getter. No DI framework.
- **GUD-002**: All Microsoft Graph calls go through the official Microsoft Graph Python SDK (`msgraph-sdk`) wrapped by the `microsoft-agents-a365-*` packages. No raw `httpx.post` to Graph.
- **GUD-003**: Pydantic-models-and-dataclasses convention from [feature-agent-governance-toolkit-1.md](feature-agent-governance-toolkit-1.md) GUD-003 continues. New types live in `api/server/services/governance/agent365_types.py`.
- **GUD-004**: Tests live under `tests/api/server/services/governance/test_agent365_*.py`. No new top-level test directory.
- **PAT-001**: Two identity facets per agent — mesh DID (Ed25519, internal cryptography) and Entra ID (OAuth, tenant resources) — bound by ONE registry row. Adding a third identity facet is forbidden; if a future system needs a third id (e.g. SPIFFE for cross-cloud workload identity) it must derive from one of the two existing facets.
- **PAT-002**: Single chokepoint per side stays single. Transport selection is a switch *inside* the chokepoint, not a new chokepoint. DRY by construction.
- **PAT-003**: Provisioning is declarative and idempotent. The `AgentRegistryEntry` is the source of truth; `make agt365-provision` reconciles the tenant to the registry. Drift is detectable by `make agt365-verify`.
- **PAT-004**: The trust-score → Conditional Access pipeline is push-based and async. The `RewardEngine` callback fires; the Graph PATCH is non-blocking. Mesh-side revocation is immediate (synchronous); Entra-side revocation lags by ≤ 5 seconds (best-effort). The mesh-side revocation is the authoritative containment; Entra-side is defence-in-depth.

## 3. Alternatives

- **ALT-001**: **Drop the mesh DID entirely; Entra Agent ID is the only identity.** Rejected. The hash-chained ledger and `agt verify` story rely on Ed25519 signatures that an auditor reproduces from public keys committed to `data/governance/agent-pubkeys/`. Entra-issued certificates rotate frequently and aren't designed for this kind of long-horizon audit-blob verification — the auditor would need historical Entra metadata to verify entries from months ago. Two-facet model preserves both stories.
- **ALT-002**: **Drop the Entra Agent ID; use Entra app-registration with a generic service-principal pattern.** Rejected. Generic app registrations cannot get an Agent User, cannot receive Teams @mentions, do not appear in the org chart, and are not subject to the agent-specific Conditional Access surface Microsoft is investing in. We would lose the demo-narrative-friendly "the agent has its own mailbox and Teams presence" beat that resonates with M365-centric customers.
- **ALT-003**: **Replace AGT entirely with Agent 365 tooling SDK + Microsoft Purview / Entra audit logs.** Rejected. AGT's `agt verify` produces an auditor-reproducible cryptographic proof from a single blob without any tenant access; Purview audit logs require tenant log access and don't carry the deterministic policy-bundle hash. The two are complementary surfaces, not substitutes.
- **ALT-004**: **Push trust score into Microsoft Sentinel as a UEBA signal instead of into Entra Conditional Access.** Considered. Sentinel UEBA gives richer risk modelling but only fires alerts to a SOC, not real-time access control. Conditional Access is the actual containment lever. Sentinel is a complementary layer (out of scope for this plan; could be a follow-up).
- **ALT-005**: **Provision Entra blueprints lazily on first use rather than at boot.** Rejected. Lazy provisioning means the first tool call from a new agent has 5–10 second latency for Graph round-trips and partial-failure modes (blueprint created, instance failed). Boot-time idempotent provisioning is simpler and matches the operator runbook expectation ("after `make agt365-provision` completes, all agents are ready").

## 7. Risks & Assumptions

- **RISK-001**: Microsoft Agent 365 SDK Python packages may not all be on PyPI yet. Phase 1 TASK-005 explicitly halts the plan if any package import fails, so this is a fail-loud risk; mitigation is to defer the plan until packages are available or to wrap the missing pieces ourselves (last-resort, breaks CON-001).
- **RISK-002**: Entra custom security attribute writes from a service identity require careful permission scoping. If the provisioner's own Entra app lacks the right Graph permission, score-update PATCHes will fail silently. Mitigation: SEC-002 makes the failure log-loud and the mesh-side revocation is authoritative — defence-in-depth design tolerates Entra-side flaps.
- **RISK-003**: Conditional Access policy publish that targets the wrong group could lock out legitimate human users. Mitigation: SEC-006 requires explicit `--i-have-reviewed-the-policy` flag and the policy text targets only the `agt-at-risk` Entra group which contains only service principals (groups.json restricts membership type).
- **RISK-004**: Per-engagement tenant cost. Each agent with `requires_m365_user=True` consumes one M365 E5 + Teams Enterprise + Copilot license set. At fleet scale (8+ domains × multiple agents), license cost is non-trivial. Mitigation: CON-003 makes license assignment operator-gated with explicit Make target; the default `requires_m365_user=False` keeps cost zero unless explicitly enabled.
- **RISK-005**: API churn in the GA-but-young Agent 365 SDK packages could break the provisioner mid-engagement. Mitigation: CON-001 narrows the import surface to one file; pin to an exact patch version; release-notes scan is a quarterly chore.
- **RISK-006**: Graph token TTLs (typically 1 hour) require token refresh logic. The `microsoft-agents-a365-runtime` package handles this; if it doesn't, the provisioner's in-memory cache becomes stale and Graph PATCHes return 401. Mitigation: TASK-013 must validate the SDK's documented refresh behaviour during implementation; if absent, add a manual refresh hook on the provisioner.
- **RISK-007**: Two-plane revocation lag (mesh-immediate, Entra ≤5s) means a rogue agent has a 5-second window where the mesh kill-switch denies tool calls but the agent could still acquire an Entra token. Mitigation: PAT-004 documents this as a known limitation; the Entra path is defence-in-depth, not the primary containment.
- **ASSUMPTION-001**: The engagement-POC dev tenant has Entra ID P1 or higher (custom security attributes available).
- **ASSUMPTION-002**: The engagement security lead is the named operator for tenant-bootstrap and CA-policy publishing; the developer team does not run those Make targets against any production tenant.
- **ASSUMPTION-003**: Microsoft Graph rate limits do not become a constraint for a fleet of < 100 agents. At larger scale (hundreds of agents with frequent score updates), the score-change callback would need batching or queueing — out of scope for this plan.
- **ASSUMPTION-004**: The AGT plan's `RewardEngine` is wired and producing score updates in the substrate (it is, per [feature-agent-governance-toolkit-1.md](feature-agent-governance-toolkit-1.md) Phase 5). If the RewardEngine isn't producing updates, the trust-score → CA bridge does nothing — but it also does no harm.
